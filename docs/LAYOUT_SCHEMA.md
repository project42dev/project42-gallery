# Project 42 Layout Bundle Contract

A layout bundle is the second of the Gallery's two independent appearance axes.
A **theme** owns identity -- colour, typeface, component treatment. A **layout**
owns *composition* -- how wide the content runs, how much air sits between
things, how large the type steps, how round the corners are. A site selects one
of each, and the two are chosen independently: any theme must render correctly
under any layout.

That independence is the whole reason the boundary is enforced rather than
merely described. A layout that declared a colour would make some
theme x layout pairs look wrong and others right, and "select a layout" would
quietly become "select a second theme". So the rule is absolute:

> **A layout bundle may not declare a colour or a font family.**
> No `#hex`, no `rgb()`/`rgba()`, no `hsl()`/`hsla()`, no `font-family` --
> not in `layout.json`, not in `layout.css`.

`scripts/validate-layout-bundles.mjs` enforces this on the manifest values and
on the stylesheet, and `scripts/build-layouts.mjs` refuses to emit a bundle that
breaks it.

## The files

A layout bundle is a directory under `layouts/` containing exactly two files:

| File | Role |
| --- | --- |
| `layout.json` | The manifest. **The single source of truth.** |
| `layout.css` | Generated from the manifest. Never hand-edited. |

`layout.css` is generated by `npm run build:layouts`. The validator regenerates
nothing, but it does check that every token in the manifest appears in the
stylesheet, so a hand-edited stylesheet fails the gate. This is the same rule
themes follow, for the same reason: a manifest that is not the source of truth
silently stops being read.

## `layout.json`

```json
{
  "id": "standard",
  "name": "Standard",
  "description": "The default composition: balanced content width, comfortable spacing rhythm, and a moderate type ramp.",
  "author": "Project 42 Core Team",
  "version": "1.0.0",
  "assets": {
    "styles": "layout.css"
  },
  "tokens": {
    "--p42-shell": "min(1180px, calc(100vw - 40px))"
  }
}
```

| Field | Required | Rule |
| --- | --- | --- |
| `id` | yes | Must match `^[a-z0-9]+(?:-[a-z0-9]+)*$` **and** the directory name. |
| `name` | yes | Human-readable label shown in the preview matrix. |
| `description` | yes | One sentence saying who the composition suits. |
| `version` | yes | Semver. |
| `author` | no | Attribution. |
| `assets.styles` | no | Defaults to `layout.css`. |
| `tokens` | yes | Must declare **every** token in the vocabulary below -- no more, no less in spirit; a missing one is a hard failure. |

## The composition vocabulary

All 32 tokens are required. A missing token is not a soft default -- it means
that surface silently inherits whatever the previously selected layout left
behind, which is a cross-layout bug that only appears when a user switches.

### Measure and gutter

| Token | What it controls |
| --- | --- |
| `--p42-shell` | The content column width. Always a `min()` against `calc(100vw - <gutter*2>)` so it never overflows a narrow viewport. |
| `--p42-gutter` | The minimum breathing room between the shell and the viewport edge. |

### Spacing scale

| Token | Typical role |
| --- | --- |
| `--p42-space-2xs` | Icon-to-label gaps. |
| `--p42-space-xs` | Inline chip padding. |
| `--p42-space-sm` | Tight stacks. |
| `--p42-space-md` | The base rhythm unit. |
| `--p42-space-lg` | Between related blocks. |
| `--p42-space-xl` | Between unrelated blocks. |
| `--p42-space-2xl` | Within-section separation. |
| `--p42-space-3xl` | Major separation. |

### Rhythm

| Token | What it controls |
| --- | --- |
| `--p42-section-gap` | Vertical space between page sections. Fluid (`clamp()`). |
| `--p42-block-gap` | Space between blocks inside a section. |
| `--p42-stack-gap` | Space between stacked items inside a block. |

### Density

| Token | What it controls |
| --- | --- |
| `--p42-card-padding` | Interior padding of every card surface. Fluid. |
| `--p42-control-height` | Minimum height of buttons and inputs. Keep at or above `2.75rem` for a comfortable tap target unless the layout is explicitly dense. |
| `--p42-control-padding` | Interior padding of controls, as a `<vertical> <horizontal>` pair. |

### Radii

| Token | What it controls |
| --- | --- |
| `--p42-radius` | The default corner radius for cards and panels. |
| `--p42-radius-small` | Chips, inputs, small surfaces. |
| `--p42-radius-large` | Hero and feature surfaces. |
| `--p42-radius-pill` | Fully rounded controls. Effectively always `999px`. |

### Type ramp

The ramp is a size scale, not a set of element rules -- the theme decides which
element wears which step.

| Token | Typical role |
| --- | --- |
| `--p42-step--1` | Fine print, captions. |
| `--p42-step-0` | Body copy. |
| `--p42-step-1` | Lead paragraph. |
| `--p42-step-2` | Card and section headings. |
| `--p42-step-3` | Page-section headings. Fluid. |
| `--p42-step-4` | Page headings. Fluid. |
| `--p42-step-5` | Display / hero. Fluid. |

Steps 3 to 5 must be fluid (`clamp()`), because they are the sizes that break a
narrow viewport if they are fixed.

### Tracking

Letter-spacing tightens as type grows, so tracking is part of the ramp.

| Token | Pairs with |
| --- | --- |
| `--p42-track-5` | `--p42-step-5` |
| `--p42-track-4` | `--p42-step-4` |
| `--p42-track-3` | `--p42-step-3` |
| `--p42-track-2` | `--p42-step-2` |

Tracking values are negative ems and should get *less* negative as the step gets
smaller. A tracking value that is too negative at a small step is what makes
letters collide.

### Grid

| Token | What it controls |
| --- | --- |
| `--p42-grid-cards` | The `grid-template-columns` value for card grids. Always `repeat(auto-fit, minmax(<min>, 1fr))` so the grid reflows rather than overflowing. |

## `layout.css`

Generated. It contains exactly one rule, scoped to the layout's own id:

```css
:root[data-layout="standard"] {
  --p42-shell: min(1180px, calc(100vw - 40px));
}
```

Two rules the validator enforces on the scope:

- The stylesheet **must** scope to `[data-layout="<its own id>"]`.
- It **may not** scope any rule to a different layout's id. A bundle that
  styles another layout is not selectable independently.

## Layouts must actually differ

The validator hashes each manifest's `tokens` object and rejects two bundles
that resolve to identical composition. This rule exists because the layout
bundles were once roughly 120-byte stubs that set only `--p42-shell` and were
otherwise the same file three times -- the shape of a system with none of the
substance. Three bundles that render identically are not three layouts.

## The published layouts

| | Compact | Standard | Wide |
| --- | --- | --- | --- |
| Measure | `min(960px, …)` | `min(1180px, …)` | `min(1560px, …)` |
| Gutter | `24px` | `20px` | `16px` |
| Card padding | `clamp(1rem, 2vw, 1.4rem)` | `clamp(1.5rem, 3vw, 2rem)` | `clamp(2rem, 3.5vw, 2.75rem)` |
| Default radius | `16px` | `24px` | `30px` |
| Page heading | `clamp(1.9rem, 3.6vw, 3.1rem)` | `clamp(2.3rem, 5vw, 4.5rem)` | `clamp(2.6rem, 5.6vw, 5.2rem)` |
| Card grid minimum | `220px` | `280px` | `330px` |
| Suits | Reference-heavy reading | Reading-led sites | Large displays, presentation |

## Authoring a new layout

1. Copy `layouts/standard/` to `layouts/<your-id>/`.
2. Edit `layout.json`: set `id` (matching the directory), `name`, `description`,
   `version`, and every token you want to change.
3. Run `npm run build:layouts` to regenerate `layout.css`.
4. Run `npm run build:matrix` so the preview matrix includes the new
   theme x layout combinations.
5. Run `npm test`. It must exit 0.

Check the result against **every** theme in the preview matrix, not just one.
A layout is only correct if it is correct under all of them -- that is what
choosing the two axes independently means.

## Where layouts are consumed

The portal reads `--p42-shell` and the rest from whichever `layout.css` is
installed, selected by the `data-layout` attribute on `:root`. Unlike the theme,
which is a deployment-owned choice, the layout is a browser preference the
visitor can change; both are bounded by the set the deployment installed.

See also [THEME_SCHEMA.md](THEME_SCHEMA.md) for the other axis and
[THEME_CORRECTNESS_SPEC.md](THEME_CORRECTNESS_SPEC.md) for the rules that make a
theme shippable.
